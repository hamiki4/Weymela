# API boundaries

The API is a role-authorized façade over Application use cases. Public/read boundaries: active Promotion discovery and public Creator portfolio projections. Business boundaries: wallet/deposits, Promotion CRUD/funding/publishing, applicant review, allocation, and own reporting. Creator boundaries: eligible discovery, join requests, content submission, view verification status, earnings, and payout requests. Customer boundaries: eligible Hybrid discovery, opaque short-lived Offer QR, cashback. Cashier boundaries: scan/present/confirm verified-sale checkout. Admin boundaries: configuration, promotion control tower, reconciliation, payouts, settlements, audit, and support.

No endpoint accepts client-supplied financial splits or trusts hidden UI. Commands require idempotency keys and return least-privilege projections. API contracts distinguish draft, reservation, allocation, event, and settlement resources; no V2 route or migration is reused.

Phase 4 service entry points are VerifiedViewService (go-live/refresh/pause), CheckoutService (issue/resolve/redeem), PayoutService (eligibility/prepare/mark-paid/settle) and FinancialQueries (role-specific financial reporting). API and Worker remain unwired skeletons. The host must supply a trusted IVerifiedViewProvider and IPublicIdentityDirectory; no live integration or permissive default is registered. Manual checkout has only a resolver/binding seam into the same sale posting path. Future HTTP adapters must translate ApplicationFailure kinds, validate authentication and never return an EF entity or log/serialize raw QR commands.
